# 1.0 — Komponenten & Feature-Gruppierung

Draft der 1.0-Struktur: welche Komponenten es gibt, welche Features sie tragen
und was ein PR **mindestens anfassen** muss, damit keine Dead Arms/Stubs entstehen.

> Ergänzt [`FULL_CHAIN_RULE.md`](FULL_CHAIN_RULE.md) (#394) auf Komponenten-Ebene.
> Die dortige „volle Kette“ (Game → rbbridge.dll → pipe_bridge → WebUI, Read
> **und** Write sichtbar) ist die Voraussetzung für jedes Contract-Item hier.

## Zielbild 1.0

- **Ein** Dedicated-Server, **Solo**: der Spieler spielt gegen sich selbst
  (SP/Mirror-Prinzip, siehe `tournament/README.md` SP-Mode).
- **Backend für 1.0 = `rbbridge.dll` (C++) + `pipe_bridge` (HTTP) + Web-UI
  Cockpit als „manueller Operator“.** Kein autoritativer Rust-Referee nötig —
  der Operator klickt die Commands selbst.
- **Rust-Backend / Referee = 1.1**, abgeleitet aus den Learnings der Web-UI
  (welche Commands der Operator wirklich braucht).
- **Lua-Mod = reine HUD-/Display-Schicht**, keine Business-Logik (seit #378).

## Die 1.0-Laufzeitkette

```
Game (DedicatedServer)
   └─ rbbridge.dll   (native C++ Read/Write)     [Komponente 2]
        └─ pipe_bridge.exe  (HTTP)               [Komponente 3]
             └─ Web-UI Cockpit (Operator)        [Komponente 4]
                  └─ Caddy-Proxy (extern routen) [Komponente 6]

Client Mod (HUD)  [Komponente 1]  ← liest denselben State (via Bridge/Cockpit)
Dedicated-Server-Setup [Komponente 5]  ← hält das alles am Laufen
```

## Full-Chain: was ein PR anfassen muss

**Regel (ein Satz):** Ein Feature ist erst fertig, wenn die Kette bis zur
**sichtbaren Verwendung** steht — nicht wenn nur der C++-Primitiv/Offset da ist.

| Feature liegt in                       | PR muss **mit anfassen**                                                     | Negativ-Beispiel (Dead Arm)            |
| -------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------- |
| **rbbridge.dll** (Read/Write-Primitiv) | `rbbridge.c` **+** `pipe_bridge.c` **+** Cockpit-Feld/Button **+** Host-Test | nur `dispatch_*`, keiner ruft's → Stub |
| **Bridge** (HTTP-Route)                | `pipe_bridge.c` **+** `rbbridge.c` (falls neues cmd) **+** Cockpit           | Endpoint ohne Verbraucher              |
| **Web-UI Cockpit** (Feld/Button)       | `cockpit.html` **+** `pipe_bridge.c` **+** ggf. `rbbridge.c`                 | Feld ohne Endpoint                     |
| **Client Mod (HUD)**                   | `client-mod/lua` **+** Cockpit/Bridge (Datenquelle)                                 | HUD zeigt Wert, den keiner liefert     |
| **Dedicated-Server-Setup**             | `deploy/` **+** Compose/Wine **+** Boot-Test                                 | Config ohne Boot-Nachweis              |
| **Caddy-Proxy**                        | `deploy/roles/website` **+** Route **+** curl-Nachweis                       | Route ohne Test                        |
| **Deploy/CI**                          | Workflow **+** Rolle **+** hermetic Test                                     | Workflow ohne Test                     |

**Stub-Ausnahme:** Ein bewusst offener Arm ist nur erlaubt, wenn er `# see issue <n>`
trägt — dann ist es ein **getrackter Gap**, kein toter Code.

**Beispiel C++-Bridge (wie im Gespräch):** ein `add_resource`-Feature ist erst
done, wenn `rbbridge.c` → `pipe_bridge.c` → Cockpit-Button → Host-Test **im
selben PR** stehen. Ein reiner `dispatch_*` ohne UI-Verbraucher ist ein Stub und
wird nicht gemergt.

## Feature-Gruppierung je Komponente

### 1 · Client Mod (Lua) — HUD

- `mod_load`-Marker (env/ref, #483) — vorhanden.
- HUD-Anzeigen: Wave-Counter, HQ-HP, Ressourcen, Runden-Zustand.
- **Accept:** HUD-Feld rendert einen Wert, den die Bridge/Cockpit **wirklich
  liefert** (kein hartkodierter Platzhalter).

### 2 · Server-DLL (rbbridge.dll)

- `get_state` (carbonium/ironium/mission_flow/creatures_difficulty) — vorhanden.
- `add_resource`, `activate_mission_flow`, `deactivate_mission_flow`,
  `natural_waves`, `creatures_difficulty`, `end_game` (Win/Lose via
  `MissionService::FinishCurrentMission`) — vorhanden.
- 1.0-Kandidaten (aus `archive/v2` wiederbeleben): HQ-Read (`hq_hp`/`hq_dead`),
  `restart_map`, Player-Count.
- **Accept:** `FULL_CHAIN_RULE.md` DoD — RE belegt, DLL-Read/Write, Bridge-Route,
  WebUI-Feld/Button, End-to-End-Beweis.

### 3 · Bridge (pipe_bridge.exe)

- HTTP-Routen: `/health`, `/get_state`, `/add_resource`,
  `/activate_mission_flow`, `/deactivate_mission_flow`, `/end_game`, `/probe`,
  `/creatures_difficulty`, `/natural_waves`.
- **Accept:** jede Route hat einen rbbridge-Verbraucher **und** einen
  Cockpit-Aufrufer + Test.

### 4 · Web-UI Cockpit

- Read/Write-Ressourcen, Wellen-Steuerung, Server-Control-Panel (Plane B).
- **Accept:** Feld (Read) **und** Button (Write) sichtbar; `curl`-Gegenprobe.

### 5 · Dedicated-Server-Setup

- Atomarer Boot-Test, Env-Isolation (dev/prod/test), Pfad-Schema (#483/#496).
- **Accept:** Kaltstart → genau **ein** `mod_load status=ok`; `docker inspect`/`ls`
  belegen per-env-Isolation.

### 6 · Caddy-Proxy

- `rift.projectmellon.de` → Host-Caddy → `rift-caddy` → Stack-IO.
- **Accept:** `/tournament/health`-artiger Endpoint `200` über die öffentliche
  URL; basic_auth greift; kein Regress für Statics/`/mods/*`.

### 7 · Rust Backend / Referee (1.1)

- Referee-State-Machine (`ready`→`rb_wave`, `wave_done`→next, `hq_destroyed`→
  reset) — existiert als Logik, **Egress/Ingress sind auf `main` abgehängt**.
- 1.1: aus Web-UI-Learnings den echten Command-Satz ableiten, dann die Kette
  nativ schließen (kein `rb_wave`/`rb_reset`-Lua).

### 8–12 · Cross-cutting

- **Deploy/CI:** Pipeline grün, Boot-Test, Path-Filter (#393).
- **Observability/Crash:** Crash-Collector + PDB-Symbolik (#462/#480/#481).
- **Session-Logging:** Session-Recorder + Traceability (#280, #392).
- **Test-Harness:** Host-Test (`rbbridge-hosttest`), Boot-Test, Playtest-Protokoll
  (`PLAYTEST_1.0.md`).
- **Docs:** Concept, Deployment, RE-Befunde, dieses Dokument.

## Definition of Done (Feature, 1.0)

- [ ] Kette steht (Full-Chain, s. o.) — Read **und** Write sichtbar.
- [ ] Host-/Unit-Test grün; Player-Test als **Offener Punkt** markiert (nicht
      „erledigt“).
- [ ] Kein Dead Arm — oder explizit `# see issue <n>`.
- [ ] Thread-Modell respektiert (#378): Lua nur auf Lua/main-Thread, native
      C++-Reads/Writes thread-agnostisch.
- [ ] Kein `ok:true`-Falsch-Grün (#288/#376): „proven“ = sichtbarer Effekt.
