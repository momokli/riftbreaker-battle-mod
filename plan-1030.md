## 1 · Ziel & DoD-Abgleich

Nach einem beendeten VS-Match soll aus der Lobby heraus direkt ein Rematch derselben
Paarung gestartet werden: **gleiche zwei Spieler**, **gleiche A/B-Weltzuordnung**, aber
**zwei frische (kalte) Welten**. Die alte Instanz muss vorher sauber gestoppt sein.

| DoD (aus Issue #1030) | Umsetzung im Plan |
|---|---|
| Rematch aus der Lobby startet neues Match derselben Paarung | Neue Route `POST /queue/rematch` (Relay → Queue-Dienst) orchestriert: alten Match finishen/cleanen → Referee `POST /rematch` → zwei **neue** Kalt-Instanzen (`queue-<neu>-a/b`) → `/lobby` (neue `match_id`) → `/ready`. UI-Button „Rematch" im Lobby-Relay. (US2–US5) |
| Lifecycle-Regeln aus #183 beruecksichtigt (dokumentiert) | §5 „Lifecycle-Defaults": konservative, benannte Defaults, Verweis auf #183. Doku-Update in US6. |
| Kein Zombie-Match | §4 „Anti-Zombie & Idempotenz": alte Instanzen **vor** neuen stoppen; Referee-Reset **vor** Provisionierung; Idempotenz-Map; `_lock`. (US1–US3) |

**Abgrenzung (nicht Teil von #1030):** Match-Result-UI (#999), Disconnect-/Crash-Recovery,
MMR/Ranking, `team_size > 1`.

## 3 · Schnittstellen (Vertrag)

### 3.1 Queue-Dienst — NEU `POST /queue/rematch`
Body (genau **eine** der beiden Angaben, sonst `400 bad_request`):
```json
{ "match_id": 7 }          // bevorzugt: deterministisch
{ "identitaet": "str:<A>" } // Komfort: letztes (finished) Match dieses Spielers
```
Response `200`:
```json
{ "ok": true, "rematch_of": 7, "idempotent": false,
  "match": { "match_id": 8, "mode": "vs", "state": "ready", "result": null,
             "participants": [ { "identitaet": "str:<A>", "world": "A",
                                 "instance": "queue-8-a", "endpoint": "127.0.0.1:63xx" }, … ],
             "assignments": [ … ] } }
```
`idempotent:true` + derselbe `match` bei wiederholtem Aufruf mit **derselben** alten `match_id`
(kein zweiter Start). Fehlerformat wie bestehend `{"ok":false,"reason":…,"detail":…}`.

| Situation | HTTP | reason |
|---|---|---|
| Body ohne/mit ungueltigem `match_id`/`identitaet` | 400 | `bad_request` |
| `match_id` unbekannt | 409 | `unknown_match` |
| Spieler hat kein Match | 409 | `no_match` |
| Quell-Match nicht `finished` (noch laufend/ready) | 409 | `match_not_finished` |
| Referee nicht in `finished`/`lobby` (z. B. `running`) | 409 | `referee_rematch_failed` |
| Cleanup der alten Instanzen scheitert | 503 | `cleanup_failed` |
| Provisionierung/`lobby`/`ready` der neuen Welten scheitert | 503 | `provision_failed` |
| Queue-Backend/Referee nicht erreichbar | 502/503 | `unreachable` (aus `_http_json`) |
| ohne/mit falschem Bearer (wenn `QUEUE_TOKEN`) | 401 | `unauthorized` |

### 3.2 Referee — BESTEHEND `POST /rematch` (nur Reset)
`{}` → `{"phase":"lobby","rematches":8}`, `409 conflict` wenn Phase `running`
(`state.rs:866`). Wird **intern von der Queue** aufgerufen (kein neuer Endpunkt noetig).
Die neue `match_id` wird danach per `POST /lobby` gesetzt; der Referee echoisiert sie
als `teams.{A,B}.match_id` (`state.rs:219`, `view()`).

### 3.3 Relay — NEU `POST /queue/rematch` (Lobby-Route + UI)
Proxy an Queue-Dienst (`/queue/rematch`); Body `{match_id}` **oder** `{identitaet}`.
Bei Erfolg pinnt der Relay — wie bei `POST /queue` — **alle** Teilnehmer der neuen
Match-Antwort auf ihre **neuen** GNS-Endpoints (`parseQueueAssignments`, `g_queueState`).
Fehler wie §3.1 durchgereicht, plus `503 queue_unconfigured`, `502 queue_unreachable`,
`400 bad_request` (Body ungueltig, kein Outbound).
Optional (Operator-Paritaet, **nicht** im Spieler-UI): `POST /referee/rematch` reicht
`POST /rematch` an den Referee durch (Bearer) — **nur Reset, keine neuen Welten**;
als solches klar dokumentiert, um Verwechslung mit dem Queue-Rematch zu vermeiden.

## 4 · Anti-Zombie & Idempotenz (Kern des Features)

**Orchestrierungs-Reihenfolge** (in `QueueCoordinator.rematch`, unter `self._lock`):
1. Quell-Match auflösen (`match_id` bzw. letztes Match der `identitaet`); pruefen `state == finished`.
2. Idempotenz: `_rematch_of.get(old_id)` vorhanden → **sofort** den bekannten neuen Match
   zurueckgeben (`idempotent:true`), **kein** Start.
3. `finish(old_id)` → garantierter, **idempotenter** Kalt-Stop beider Alt-Instanzen
   (`_cleanup`, Fail-fast). Scheitert der Stop → `503 cleanup_failed`, **kein** neuer Match.
4. Neuen Match-Record anlegen (`core.create_rematch(old)`): gleiche `teams`/Weltzuordnung,
   neue monotone `match_id`, State `provisioning`, Feld `rematch_of=old_id`.
5. **Referee `POST /rematch`** (Reset → Lobby; Spieler bleiben registriert). 409 →
   neuen Record `failed`, **keine** Instanz gestartet (kein Zombie), `409 referee_rematch_failed`.
6. Kalt-Provisionierung zweier **frischer** Instanzen `queue-<neu>-a/b` (wie `_provision`).
7. Referee `POST /lobby {player,world,new_match_id}` ×2, danach `POST /ready {world}` ×2 (Reihenfolge wie #1025).
8. `_rematch_of[old_id] = new_id` setzen + `_persist()`; Erfolg zurueckgeben.

**Zombie-Vermeidung**
- Alt-Instanzen werden **vor** dem Start der neuen gestoppt (Schritt 3 < Schritt 6).
- Referee-Reset **vor** Provisionierung (Schritt 5 < Schritt 6): ein 409 laesst keine Welt starten.
- Jeder Fehler nach Schritt 6 rollt **die gestarteten** Instanzen zurueck (`stop`, best-effort)
  und markiert `failed` — Muster aus `_provision` (`queue_flow.py:305-362`).
- Doppel-Tick/Parallel-Request: `_lock` (RLock) serialisiert; die Map wird erst **nach**
  Erfolg geschrieben → parallele Anfragen erzeugen **maximal ein** neues Match.
- Persistenz: `_rematch_of` wird in `queue-state.json` mitgeschrieben, damit ein Dienst-
  Restart die Idempotenz nicht verliert (`_persist`/`_load_state`).

**Rollback**
- Queue: fehlgeschlagener Neustart → gestartete Instanzen `stop`, Match `failed`, Map **nicht** gesetzt → Retry moeglich.
- Referee: `/rematch` bei `running` → 409, **keine** Zustandsaenderung.
- Relay: reiner Proxy, kein lokaler Zustandsmut bei Fehler (nur `g_queueState` erst bei 200).
- Gesamt: `git revert` des PR genuegt (keine Migration; neue Felder additiv, alte State-Dateien bleiben lesbar).

## 5 · Lifecycle-Defaults aus #183 (konservativ, benannt)

| #183-Frage | Default fuer #1030 | Begruendung |
|---|---|---|
| 1. Spar-Pool reset? | **Ja, reset.** Referee `rematch()` leert `team.resources` + HP; Queue startet **frische kalte** Welten (kein Warm-Reuse). | Kalte Provisionierung ist der bestehende #998-Pfad; deterministisch, kein Alt-Zustand. |
| 2. Seed/Settings identisch? | **Identisch.** Gleiche Paarung, gleiche A/B-Weltzuordnung, gleicher `env`/`provision_mode`. Kein Reseed. | DoD „gleiche zwei Spieler"; kein Seed-Mechanismus vorhanden. |
| 3. Disconnect mitten im Match | **Out of scope.** Rematch nur bei `phase=finished`. | Verweis #183. |
| 4. Ready/GO-Timeout | **Unveraendert** (#1025). | Keine neue Achse. |
| 5. Server-Crash mitten im Match | **Out of scope.** | Verweis #183. |
| 6. Wann gewertet/abgebrochen | Kein MMR; Record behaelt `result`, Rematch = **neuer** Record (`rematch_of`). | Issue-Abgrenzung. |
| 7. Rematch waehrend `running` | **Refused** (`409 referee_rematch_failed`), kein neuer Start. | Kein Zombie, konservativ. |
| 8. Cleanup-Semantik | Alt-Instanzen **immer** vor neuen gestoppt; Cleanup-Fehler blockiert Neustart. | Anti-Zombie-DoD. |

## 8 · Offene Punkte / Risiken

1. **Referee `queue_match_id` bleibt nach `/rematch` gesetzt** bis zum naechsten `/lobby`.
   Zwischen Reset und Re-Lobby echoisiert `GET /state` die **alte** `match_id` → moegliche
   Fehlzuordnung des Reconcilers. **Mitigation:** Queue setzt neue `match_id` in `/lobby`
   unmittelbar nach Reset (Schritt 7); Reconciler wertet nur `finished` aus und der neue
   Match ist `provisioning`. → in US4/US6 dokumentieren; ggf. Referee-seitig `queue_match_id`
   in `rematch()` leeren (Entscheidung im Dev-Schritt).
2. **Doppel-Klick im UI** → Idempotenz-Map faengt es ab (US2/US3); UI deaktiviert Button
   waehrend des Requests.
3. **#183 bleibt offen** → Defaults in §5 sind bewusst konservativ und im Doku-Update als
   revidierbar markiert; kein Block.
4. **TOURNAMENT_TOKEN/`WRITE_ROUTES`** und Caddy `@write` muessen `/rematch` bereits fuehren
   (`api.rs:266` zeigt es; Caddy-Config im Dev-Schritt gegenpruefen). Relay→Queue nutzt `QUEUE_TOKEN`.
